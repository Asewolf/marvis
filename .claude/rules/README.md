# Rules

Standing instructions scoped to a subject. A rule file loads when its topic comes up,
which keeps the context small while still making the standards non-negotiable when they
apply.

## Rule or memory?

**Memory** is a fact. "I use pnpm." "The staging DB is read-only."

**A rule** is a standard with enough surface area to need sections. Once you have four or
five memories orbiting one subject, they want to be a rule.

## Writing one

- Name it after the subject: `security.md`, `writing-voice.md`, `deployment.md`
- Lead with the hard rules, the ones with no exceptions
- Give the reason. A standard without a why gets applied stupidly at the edges
- Be concrete. Name the commands, the paths, the limits
- Say what NOT to do as explicitly as what to do

## Examples in this kit

- `writing-voice.md` - a voice standard, the shape a "how my writing should sound" rule takes
- `security.md` - a hard-requirement rule for anything client-facing

Both are meant to be edited, not adopted as written.
